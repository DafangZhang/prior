> 3. **「不符合需求文档规范」缺少可执行的判定**：本轮把产品文档的规范（来自 `product-manager-toolkit` skill 的 PRD 模板）提炼成**必需章节清单**，作为流程 2 的一类发现：缺验收标准、缺范围外、缺异常与边界、缺数据口径等。
>
> 另外本轮把语料的业务事实（版本对、模块分布、日期覆盖、文档类型）落成数字写进 §2.4，作为验收的基线。

## 1. 执行摘要

**问题**：产品历史需求文档（172 份，跨越 2023–2026）只以文件形态存在。新人接手一个模块时，看不到「这个功能点现在的规则是什么、上一次是谁在哪份文档里改的」；评审一份新文档时，只能靠人肉翻阅历史文档，既慢又漏。更麻烦的是，这些历史文档**已经无法追溯评审**——它们是既成事实，缺的是结构化的归档。

**方案**：把文档处理拆成两条流程，共用一套内核与一份知识库：

- **流程 1「文档直接入库」**：存量文档批量建档。解析 → 切块 → embedding → 抽取所属系统/模块、文档日期、文档类型 → 入库，作为历史基线。产出是**可检索、可按日期排序、按模块分组**的知识库。
- **流程 2「文档分析入库」**：新产品文档进来时，检索历史 → 交叉比对 → **逐功能点记账**（这条规则以前是什么、现在改成什么、影响谁）+ **四类评审发现**（逻辑漏洞 / 不明确 / 一句话需求 / 变更信号）+ **规范性检查**（缺验收标准等）。

**业务影响**：
- 评审从「读十份历史文档」变成「看一条账本 + 若干条带原文的发现」；
- 功能点规则有了版本沿革，**改错的代价从「上线后才发现」前移到「评审会上」**；
- 存量文档按模块 + 日期可查，新人接手的成本从「问人」变成「查库」。

**成功度量**（详见 §8）：
| 度量 | 目标 |
|---|---|
| 存档：日期覆盖率 | ≥ 85%（当前 151/172 = 87.8%） |
| 存档：模块覆盖率 | ≥ 95%（当前 152/172 = 88.4%，本轮目标） |
| 版本沿革：真实版本对上产出 `modified` 的比例 | 3 组版本对全部命中（当前 0 组，本轮目标） |
| 评审：发现的**可核查率**（引用能在新文档中定位） | 100%（已是硬约定，代码强拦） |
| 评审：人工确认率 | ≥ 60%（需要评测集，本轮只建度量口径） |

## 2. 问题定义

### 2.1 用户与场景

| 角色 | 场景 | 现在的做法 | 期望 |
|---|---|---|---|
| 产品经理（提需求方） | 写了一份新需求，想确认有没有和半年前的规则冲突 | 凭记忆 + 搜索历史文档 | 提交文档 → 拿到冲突清单与历史出处 |
| 评审人（产品负责人） | 评审新文档 | 人读，凭经验问「异常流程呢」 | 文档自身的问题（缺验收标准、一句话需求）自动列出 |
| 接手人（新人 PM） | 接手某模块 | 翻遍该模块的历史文档 | 按模块看「当前规则基线」+ 变更沿革 |
| 归档人（我自己） | 存量文档散落各处 | 手工整理命名与目录 | 批量入库，自动定日期与模块 |

### 2.2 现状与代价

- 历史文档**无法评审**：它们是既成事实，需要的是归档（流程 1），不是批判。
- 规则**只存在于文件里**：同一条规则被三份文档反复描述，谁改的、改成什么，没有地方记。
- 评审**依赖记忆力**：「以前这里是不是能选多个？」——没有结构化答案。

### 2.3 根因

没有「以功能点为单位、以文档日期为序」的规则台账。文档是**文本**，不是**数据**：无法按模块查、无法按日期排、无法看沿革。

## 3. 两条流程的产品定义

### 3.1 流程 1：文档直接入库（存量建档）

**触发**：用户选择一个目录（首次全量），或后续把新拿到的旧文档丢进同一目录再跑一次。

```
选择目录
  → 逐份解析（docx / xlsx / markdown / txt / csv）
  → 规范化 + 结构感知切块（目标 300–600 字、上限 800、表格不跨块、带标题路径）
  → 抽取文档元信息：标题、版本、文档类型、【所属系统/模块】、【文档日期 + 来源 + 置信度】
  → embedding（bge-m3）
  → 写入 documents / chunks（同源 URI 幂等覆盖）
  → 追加「建档」变更记录（kind=baseline）
  → 入库摘要：成功/失败、日期覆盖率、模块分布、分块数
```

**产品规则**：

| 项 | 规则 |
|---|---|
| 幂等 | 同 `source_uri` 再次入库即覆盖，不产生第二份文档；分块与向量随之一致更新 |
| 日期 | **本轮修订**：成稿日期取「文档自己声明的最新日期」，每个来源各有权重：清单 100 > 变更日志中属于本文档版本的那一行 95 > 文档字段（创建日期）90 > 完整文件名日期 80 > 短文件名日期（230604/0812）50 > 正文散文 40 > 仅年月 30 > 文件时间 20。正文散文取最晚且不超过文件时间的日期；变更日志只取版本 ≤ 本文档版本的最晚一行（副本里留着更高版本的条目，属另一份文档）；**日期未知时不得把文件时间伪装成文档日期**（库里保留排序用的文件时间，但 `date_source=missing`，界面与 CLI 一律显示「日期未知」） |
| 模块 | **本轮新增**：模型读标题 + 章节 + 正文判定「本文档属于哪个系统/模块」，给出候选值；与确定性回退（文件名中的系统名、标题中的系统名）取一致；仍判不出则留空并在摘要里计入「无模块」 |
| 版本 | 文件名/正文中的 `V1.0.0`、`1.1.0`、`2.0` 归一化写入 `version`；无版本时留空（不猜） |
| 失败 | 单份失败不影响整批：记录失败原因（加密/损坏/空文本/解析异常），摘要列出清单 |
| 旧文档的定位 | 建档即**基线**：入库的每一条功能点规则，成为流程 2 的「before」 |

**不做**：不评审存量文档（它们已无法追溯）；不修改原文件；不删除已入库文档（除非显式删除）。

### 3.2 流程 2：文档分析入库（新文档评审 + 功能点变更账本）

**触发**：产品给了一份新产品需求文档。

```
选择新文档（可先入库，或直接分析）
  → S0 读结构：章节、术语、文档类型、规模
  → R  检索历史：按标题/模块/术语/章节/摘要生成 ≤6 条查询
        → 向量召回 + 关键词召回 → RRF 融合 → 模型重排 → 文档聚合与上下文预算
  → S1 一句话需求：把非需求写法（散文、口号）识别出来，要求写成「谁 + 做什么 + 为什么」
  → S2 明确性检查：规则层（占位符/被动无主语/模糊量词/引用未提供材料/枚举不完整/流程无异常分支）+ 模型层
  → S3 逻辑漏洞：与检索到的历史规则逐条对照，找冲突（必须引用历史片段）
  → S4 变更识别与记账：识别变更语句（原有…改为…/不再/废弃…）+ 抽取功能点与其规则 → 写台账
  → S5 汇编：去重、严重度、证据齐全性、降级说明
  → 产物：一次运行（状态 succeeded / degraded / failed）+ N 条发现 + M 条变更记录
```

#### 3.2.1 发现的四类（硬约定）

| 类型 | 含义 | 必须携带 |
|---|---|---|
| `logic_gap` 逻辑漏洞 | 与历史设计冲突、规则互相矛盾 | 新文档原文片段 **+** 历史文档证据（文档/章节/日期/片段） |
| `change_signal` 变更信号 | 相对历史规则的改动 | 同上 |
| `ambiguity` 不明确 | 缺角色/动作/规则/边界/数据口径，或引用了未提供的材料 | 新文档原文片段 + 待澄清问题 |
| `one_liner` 一句话需求 | 写成了口号或结论，无法实现 | 新文档原文片段 + 应补的要素 |

**硬约定（代码强拦，不是文档口号）**：
1. 每条发现的引用片段必须能在**新文档**中定位，否则丢弃；
2. 逻辑漏洞与变更信号拿不出历史证据时，降级为不明确的「需确认」并给出问题；
3. 置信度 < 0.5 的发现降为 S3；
4. 运行「部分成功」必须显式记录降级原因，不得把失败伪装成「0 条」。

#### 3.2.2 记录种类（功能点台账）

| kind | 何时写 |
|---|---|
| `baseline` | 该功能点第一次出现（建档） |
| `modified` | 同一功能点的规则文本与上一条记录不同 |
| `clarified` | 同一功能点、规则文本一致（本次只是把话说清楚了） |
| `deprecated` | 明确写了废弃/下线（本轮由变更语句识别，需人工确认后生效） |

每条记录带：功能点、文档、运行、`before` / `after`、影响面、原文证据、状态（`extracted` → `confirmed` / `rejected`）。

**阅读顺序（本轮修订）**：沿革要读成「从前到后」，所以账本与「当前规则」都按文档排序，而不是按入库或运行的先后：

```sql
ORDER BY (d.date_source IS NULL OR d.date_source = 'missing') ASC,  -- 有日期的在前；日期未知的不当最新
         d.doc_date DESC,                                            -- 晚的在前
         coalesce(d.version_rank, -1) DESC,                          -- 同一天按版本（V1.0.0 在 V1.1.0 前）
         c.recorded_at DESC, c.id DESC                               -- 都没有才按入库顺序
```

- 落点：`FunctionPoints` 的「当前规则」子查询、`LatestRecordBefore`、`ChangeRecords`、`Ledger`、`CurrentFacts`；人工合并后的重排（`MergeFunctionPoints` 的 `lag(...) OVER`）用同一顺序。
- `LatestRecordBefore(功能点, 文档日期)` 取**该文档写作之前（含当天）**的最后一条记录，也就是「这份文档写作时该功能点的规则」；日期未知的文档取最新一条规则。没有这个日期上界时，先分析新版再分析旧版会把旧版记成「对更新版本的修改」，沿革方向就反了。
- `documents.version_rank` 由 `ingest.VersionRank` 算出（`V1.0.0`=1000、`1.1.0`=1010、`2.0`=2000；读不出或实为日期记 -1），随入库写入；日期规则改动后可用 `prior-cli dates -rescan <目录>` 只重读日期与版本序，不动向量与账本。

#### 3.2.3 功能点身份：本轮的核心修复

**问题（实测）**：同一份购物车文档连续两次分析，同一条规则被记成两个功能点（标签分别是「购物车系统 · 机构用户购买方式 · 购买选项」与「购物车系统 · 购买流程优化 · 购买方式扩展」），于是账本出现两条 `baseline`，而不是一条 `modified`。根因：身份 = 模型命名的三段式精确匹配，而模型的命名在两次运行间会漂移。

**修复规则（判定顺序，全部确定性可测）**：

1. **规范化精确匹配**：模块/功能/主题去空白与标点、统一全半角、去掉尾部「二期/2.0/补充」等修饰后，三者全等 → 命中同一功能点，写 `modified`/`clarified`；
2. **规范化标签匹配**：完整标签（模块 · 功能 · 主题）规范化后全等 → 命中；
3. **证据足够时并入（自动）**：名称有亲缘（相似度 ≥ 0.5）**且**规则几乎同义（≥ 0.8），
   或名称本身几乎相同（≥ 0.85）时，直接写进既有功能点：规则变了就是 `modified`，没变就是
   `clarified`。依据是实测——同一份文档下一版里，模型把功能点改名成
   「PC页面头部Banner替换 · 页面元素替换」而规则文本几乎不动（相似度 0.86–1.00）。
   名称亲缘低于 0.3 时**根本不做规则比对**，避免「必须记录操作日志」这类通用句式把无关功能点凑到一起。
4. **其余 0.65 以上只给候选**：仍写一条新记录，但把候选功能点与相似度落库，界面与 CLI 标注
   「疑似同一功能点（相似度 0.72）」；
5. 人工合并（`prior-cli points -merge FROM TO`）：合并后旧记录改挂到目标功能点，并按时间重排
   `kind`——原本是 baseline 的那条若与后一条规则不同，会变成 `modified`，历史不丢且仍可读。

> 为什么 4 不自动合并：误合并会把两条不同规则的历史混在一起，这种错误比多一行更难纠正。
> 3 的门槛之所以敢自动，是因为它要求**两条证据同时成立**（名称有亲缘 + 规则几乎同义），
> 而实测中无关功能点的相似度只有 0.1–0.3，两者之间有很宽的间隔。

#### 3.2.4 规范性检查（本轮新增，来自 `product-manager-toolkit` skill 的 PRD 模板）

判定的是一份文档**作为需求文档是否合格**，与「写得对不对」无关：

| 必需章节 | 判定 | 缺失时的发现 |
|---|---|---|
| 背景与目标 | 有「背景/目的/目标/概述」类章节且有实质内容 | `ambiguity/context_missing` |
| 范围（含范围外） | 有「范围/不在本期/后续」类表述 | `ambiguity/scope_missing` |
| 功能说明（分功能点） | 有功能清单或分节的功能描述 | `ambiguity/function_list_missing` |
| 异常与边界 | 有失败/异常/超时/空态/回退等表述 | `ambiguity/exception_missing` |
| 数据口径 | 有字段、取值、上下限、统计口径 | `ambiguity/data_caliber_missing` |
| 验收标准 | 有可判定的验收条件 | `ambiguity/acceptance_missing` |

规则层的判定用章节标题与关键词；模型层补充「有章节但内容空壳」的情况。缺一项给一条发现，severity 默认 S2（验收标准缺失 S1：无法验收等于没需求）。

## 5. 交互与信息架构

| 页面 | 承接的流程步骤 | 关键信息 |
|---|---|---|
| 文档库 | 流程 1 的入口与结果 | 模块分组、日期（未知明确标注）、版本、块数、入库时间；右侧 inspector 显示该文档的元信息与分块 |
| 分析台 | 流程 2 的入口 | 选文档 → 实时阶段日志 → 取消；结束后给出条目数、变更记录数、降级说明 |

## 6. 验收标准

**流程 1**
1. 全量入库 172 份文档，成功 ≥ 170，失败逐条给出原因；
2. 日期覆盖率 ≥ 85%，且**未知的不得显示为文件时间**（界面与 CLI 一致显示「日期未知」）；
3. 模块覆盖率 ≥ 95%，模块名不与同一系统的既有写法冲突（同一系统同一写法）；
4. 同源 URI 重复入库不产生第二份文档，分块数稳定；
5. 入库摘要包含：成功/失败、日期来源分布、模块分布、块数总计。

**流程 2**
6. 一次运行给出四类发现，且**每条发现的引用都能在新文档中定位**（代码强拦）；
7. 逻辑漏洞/变更信号无历史证据时降级为不明确，并附待澄清问题；
8. 在 3 组真实版本对上，先入库 V1.0.0、再分析 V1.1.0，账本产出 `modified` 记录，且 `before`/`after` 与两份文档的实际差异一致；
9. 同一功能点的重复分析不产生第二条 `baseline`（身份解析生效），模糊匹配给出候选与相似度；
10. 规范性检查能识别「缺验收标准 / 缺范围外 / 缺异常与边界 / 缺数据口径 / 缺背景 / 缺功能清单」，各给一条可核查的发现；
11. 部分成功必须写明降级原因（模型答非所问 / 抽取失败），不得静默；
12. 界面不显示推断：拿不到真实数据的位置显示空态与原因。

**工程质量**
13. `go test ./...` 全绿；身份解析、规范判定、解码容错有单测；
14. 一次完整评审在单机（一个 Ollama）上 ≤ 6 分钟（当前实测 3–5 分钟）。

| 运行 | 文档 | 结果 |

| #16 → #17 | V1.0.0（5 条基线）→ V1.1.0（重跑） | 6 条记录：**1 `clarified`（`normalized`，相似度 1.00，写进 #16 已有功能点）**、1 候选、4 新基线 |
| #25 → #26 | `自适应-专区详情、素材详情` V1.0.0（7 条基线）→ V1.1.0 | 10 条记录：**2 `modified`**（「素材列表 · 筛选条件」：按类型/标签/时间 → 按分类/标签/版权状态；「素材详情 · 文件格式」：显示软件支持信息 → 符合平台规范），3 候选（0.71–0.75）、5 新基线 |
| #27 → #28 | `自适应-软件列表、软件详情` V1.0.0（2 条基线）→ V1.1.0 | 6 条记录：**2 `modified`**（「软件列表 · Banner展示」：Banner 图暂时写死 → 由 UI 设计提供；「软件列表 · 机构分类排序」：固定艾迪普/Adobe → 增加英伟达/浪潮等），2 候选（0.67–0.75）、2 新基线 |

两次之间的差别来自模型命名本身：同一份文档两次运行可能把系统写成「SaaS春节活动系统」「SaaS数字资产云平台」「SaaS平台」，
名称相似度随之在 0.5–0.9 之间浮动。这是本流程的固有风险（§9），对策是「候选 + 人工合并」，
而不是把阈值降到会误合并的程度。

测试方法：删掉这对文档的历史，先把 V1.0.0 分析一遍（写基线），再分析 V1.1.0（应当并入既有功能点
并记成变更）。实测过程中暴露并修掉了三个真问题：

| 暴露的问题 | 现象 | 处理 |
|---|---|---|
| 自动并入的记录没落来源 | `match_kind=normalized` 但 `matched_point_id`/`match_score` 为空，报告里看不到「并入功能点 …（0.86）」 | 并入与候选都落来源 |
| 模块名在两版之间漂移 | 模型把同一个系统分别写成「SaaS春节活动系统」与「SaaS数字资产云平台」，整标签相似度被前缀稀释到 0.58（低于 0.65），真实同一功能点没认出来 | 相似度取「功能+主题」与「整标签」的较大者，模块只通过三段式精确/规范化匹配起作用 |
| 相似度只有候选档 | 名称漂移后分数落在 0.65–0.8，只给候选，于是版本沿革又断了 | 增加「证据足够自动并入」档：名称有亲缘且规则几乎同义（见 §3.2.3） |

### 10.5 台账的诚实与取舍（本轮最后一批修复）

排查第二组版本对时暴露了三种「台账写不出来」的情形，逐一处理：

| 情形 | 现象 | 处理 |
|---|---|---|
| 模型把引用的**两端**改写 | 10 个功能点的 quote 全部核对不过，台账全空 | 长引用只要**连续 14 字**能在本文档找到即通过（按 3 字步长滑动）；改写过的句子不会连续 14 字与原文相同，跨文档污染仍被拦住 |
| 模型**自己写规则**而不是摘录（逐字重合最长只有 5 字） | 同上 | **不再丢弃**：仍记入账本，但不带证据、状态标 `unquoted`，界面与 CLI 显示「无引用（待核对）」，运行日志写明几个点是这种情况。台账的用途是跨版本追踪规则，不该被模型的引用能力否掉；但模型自述也不能冒充原文证据 |
| 模型在 / 长文档回答**被长度上限截断** | 半个 JSON，整阶段失败 | 流式解码只取完整条目，S1–S4 阶段写一行「回答达到长度上限，已按完整条目保留 N 条」 |

**发现（findings）仍然严格**：引用不在本文档就丢弃——那是对本文档的判断，没有出处就没有价值。

### 10.6 性能与稳健性

- **单次生成有上限**：模型调用此前没有 `num_predict`，长文档时模型会一直写到它自己觉得完为止——
  实测一份 9407 字的文档在 S2 阶段停了十分钟以上。现在统一 `num_predict: 2400`
  （prompt 要求的最长答案也不过几百 token），一次评审的阶段耗时因此有界。
- 各阶段耗时（本机、一个 Ollama）：S0 需求条目 ~1 分钟、R 检索含重排 ~1–3 分钟、
  S1–S4 各 ~1 分钟、S5 汇编 ~10 秒；端到端 3m05s–4m21s。

### 10.7 环境切换（本机 PostgreSQL 17.9 + pgvector）

先前跑在 5433 的容器库上（无 pgvector，向量检索走应用侧余弦）。切到本机 `127.0.0.1:5432`

- `store.Open` 增加**自动建库**：服务端报 3D000（库不存在）时，用同一个服务器的 `postgres` 库建；

- 该服务器有 pgvector → `0002` 迁移自动应用：2026 个分块全部写入 `embedding_vec vector(1024)` 并建 HNSW，
  **向量检索改为原生列：6ms**（此前应用侧余弦首次 125ms、缓存后 3ms）；

- 桌面端配置文件（`~/Library/Application Support/Prior/settings.json`）同步更新 DSN 与模型名
